# 文档契约

> 零构建静态站的文档往往只有两三份，但它们是**最贵的资产** ——
> 代码能读，决策读不出来。这份契约讲怎么让它们不腐烂。
>
> 用占位符指代：`$ARCHIVE`（归档） / `$LOG`（经验日志） / `$READER`（页内读者文档）。

## 1. 双轨：两类读者，两份文档

|  | `$READER`（读者文档） | `$ARCHIVE`（归档文档） |
| --- | --- | --- |
| 位置 | 站内，访客点开就能读 | 仓库里，维护者读 |
| 内容 | 这个站是怎么设计的、有哪些模块、变更记录 | 每一次改动的来龙去脉 |
| 谁在读 | 访客 / 未来的用户 | 未来的维护者 |
| 寿命 | 长期，**只加不改** | 永久，**只追加不删** |

**同步铁律**：两份文档若共用同一份头注（标题格式、版本号、术语表），
**改任一份就要 grep 另一份再改一遍**。这个坑会反复踩，因为两边看起来是独立文件。

**同步方向可以反着来**。判据是「**哪一边与代码一致**」，不是「谁是权威」。
机械地以归档文档为准，会把正确的镜像改错。

### 关于 `$READER` 的实现方式

零构建站常见做法是把读者文档**内联**在入口 HTML 里（`<script type="text/plain">` 之类），
而不是运行时 `fetch` 一个同级文件 —— 因为 `file://` 下 `fetch` 会被 CORS 挡（`Origin=null`），
本地双击打开就是空白。

代价是双份存储：入口文件会显著变大。这是已知的、被接受的代价，不要为了瘦身改成 fetch。

## 2. 「当前状态」章是快照，不是追加日志

`$ARCHIVE` 里最容易被写坏的一章，是「今天这个项目是什么样」。

它必须是**快照** —— 回答「现在」，而不是「都发生过什么」。常见退化路径：
每轮往这一章里追加一段，几轮之后它有几十个小节、上千行，比它要回答的问题还大。

维护契约：**下一轮做完事，改这一章，而不是另起一章。** 加新归档章时**必须同时**改：

- **模块表** —— 今天有哪些模块 / 浮层（实测，不是抄历史）；
- **改动索引** —— 一行一章的流水表，回答「第 N 章说了什么」；
- **开放项表** —— 未决问题，以及表头的**条数**。

漏掉任何一个，索引表就落后于目录表，这一章自己变成「过期的那半」。

开放项表的两个细节：

- **已销账的条目不删，划掉并写清怎么销的** —— 否则下一轮会被重新排期；
- **区分「有活没干」与「早就做完了但清单还挂着」** —— 后者比前者更值得记，
  因为它在**谎报当前态**，读的人会以为还有活。

## 3. 编号：三套编号互不相同，别混

| 编号 | 归属 | 规则 |
| --- | --- | --- |
| 归档章号 `§NNN` | `$ARCHIVE` | 项目的序号。**新章只取空号，不重编号**；改号不能全局替换，要先算准区间并断言区间内无他人内容 |
| 任务号 `#NNN` | 任务/工单系统 | 与章号**大体对应但不是一回事**；只有章标题里明写「（原 #NNN）」的才是当时的任务号 |
| 读者文档章号 `§N` | `$READER` | 与归档章号**完全不同**，是另一套 |

引用时必须带上来源（「归档 §NNN」「读者 §N」），否则读的人会去找错地方。

若三套之外还有第四套（例如某份「已知教训」表的行号），**引用时用它自己的定位方式**，不要硬套章号。

## 4. 目录表必须由脚本重生成

手改目录迟早漂移。标记包裹：

```
<!-- TOC:START -->
...
<!-- TOC:END -->
```

表头写明「数字均为实测，改动后请重跑 `<生成器>` 同步本表」。

⚠ **注意生成器对行尾的影响**：很多目录生成器用 `split('\n')` → 改 → `join('\n')`。
切分后每个元素**自带尾部 `\r`**，所以正文 CRLF 被原样还原，而**新生成的目录数组不含 `\r`**
⇒ 文件稳定地呈现「目录区纯 LF + 正文纯 CRLF」。

这是**结构性不变量，不是污染**。去「修」它会造成整文件 diff。
如果项目宁可不跑生成器，就**定点改**：只改计数行 + 追加新行，目录区其余部分一行不动。

## 5. 历史章一字不删不改

历史章是「为什么走到今天」的证据，不是错稿。

- 只在章首加指针，挡住照抄；
- 含「可执行但已失效的建议」的段落，必须加「**勿据此改代码**」指针；
- 含「已并入 X」的声称，要**验证 X 真的存在那段** —— 声称式归档最容易留下静默的信息黑洞。

## 6. 新章的五段骨架

**现象 → 根因（量出来的数字，不是感觉）→ 改法 → 验证 → 教训**

- 「根因」必须是可复算的数字或可复现的步骤，不是「可能是某某原因」；
- 「验证」要写**跑了什么、多少通过多少失败**，不写「已验证」；
- 「教训」必须是**可复用的一条**（以后遇到同类问题照着做），不是「我学到了什么」。

## 7. `$LOG` 的角色

逐次追加经验教训。**本轮没有新增就明写「无新增」**，不为凑数硬写 —— 凑数会让日志失去信号价值。

常见形态：每条扩展是**一行**块引用（`> - 🆕 **§XXX · 日期** (第N次扩展): ...`），
最后一行是汇总的「教训（N 条, A → B）」。

⚠ 行尾形态要按项目约定守恒（有的项目这份文件是全 CRLF 且**末尾无换行**）。
长文本（章正文、日志条目）**不要塞进脚本的字符串字面量** —— 正文写独立 `.txt` 再读入。

## 8. 刷数字的三条判据

1. **按数字模式全局扫，不按行号清单** —— 「行号 + 原文」靠人眼定位，漏掉的永远不会自己变绿；
2. **先判「当前态」还是「历史」** —— 这句话会不会随今天的文件变？描述现在的要刷，记录当时的要留；
3. **计数用 eval 实测，不用正则** —— 口径错了比数字错了更难发现；差值也要实测集合，不能用两个数相减。

同一个数字出现多次不是 bug，只有「描述现在」的那些该改。

## 9. 怎么快速找到该改哪里

- 先看目录区定位归档章；
- 改动索引表是**一行一章**的流水，回答「第 N 章说了什么」；
- 搜规则时按关键词全库扫，**不要凭印象猜行号**；
- 章数上百之后**不要整读** —— 读目录 + 目标章 + 关联章。
